# Codex Pulse 补丁维护

仓库：https://github.com/haochen12/codex-pulse.git

目标是在用户指定的 Codex VS Code 扩展中维护用量卡片，同时保留正常自动更新。

## 定位源码与扩展

- 优先使用当前工作区中的 Codex Pulse 仓库，核对 `package.json` 名称为 `codex-pulse`，以及 `scripts/patch-codex.cjs` 存在。技能目录位于源码的 `skills/` 下时也可定位到该仓库；安装在全局技能目录时不能假定父目录是源码。
- 未找到源码时，在用户工作区内不冲突的位置克隆上述仓库。已有源码时检查 Git remote；来源不同则保留用户的来源，不擅自替换。
- 需要 Node.js 22+ 和 Git。优先使用 PATH 中的工具，缺失时检查工作区已有工具；无法运行则报告缺失依赖，不自动进行系统级安装。
- 使用补丁工具的自动发现逻辑选择当前注册的 Codex 版本，不按目录时间或版本字符串猜测。Insiders、远程或自定义目录使用用户指定的 `--editor`、`--extensions-dir` 或 `--target`，后续命令保持相同目标参数。多个安装无法确定目标时再询问。

## 检查与更新

在源码目录执行：

```sh
node scripts/patch-codex.cjs status
```

仅请求检查时，到此报告结果，不拉取源码或修改扩展。`status` 的“结构不匹配”可能仍以退出码 0 结束，必须阅读输出，不能只看退出码。

用户请求更新或恢复卡片时：

1. 记录源码提交、当前目标扩展路径、版本及补丁状态。检查 Git 工作区和分支。保留本地修改；不要 reset、clean、强制切换分支或自动 stash。存在本地修改时先判断是否阻碍更新；需要覆盖或合并用户修改时先说明冲突。
2. 对已确认的源码 remote 执行 fetch，检查当前分支与上游差异。仅执行快进更新；分叉或没有明确上游时报告原因，不自动解决为覆盖本地提交。不要提交或推送到远端，除非用户另外要求。
3. 如果当前扩展已安装补丁且校验通过，需要更新源码或用户明确要求重新安装，先使用**更新前的源码工具**对该目标执行 `restore`，成功后再快进更新源码。若当前扩展未打补丁，直接更新源码，不恢复其他旧版本目录。若无需更新且补丁校验通过，报告已是当前状态即可。
4. 使用更新后的工具重新执行 `status`。只有“未安装补丁且结构匹配”时执行 `apply`。已安装且校验通过时无需重复应用。

```sh
node scripts/patch-codex.cjs apply
node scripts/patch-codex.cjs status
```

5. 验证最终状态是补丁已应用且文件校验通过，告诉用户在 VS Code 中运行 `Developer: Reload Window`。不要在活动对话中自动重载窗口。文件校验不能证明真实界面已显示，应区分文件安装成功与用户重载后的界面确认。

## 更新边界与失败处理

- 不修改 VS Code 更新设置、Codex 自动更新开关、扩展注册信息、版本锁定或文件权限；不安装旧版 Codex 来迁就补丁，也不创建后台监视进程自动注入。
- 官方接口用于用量数据，界面注入仍依赖扩展内部结构。遇到结构不匹配、文件被外部修改、备份损坏或恢复失败时停止当前写入流程并报告具体原因。不要跳过校验、强行替换入口或把旧版本备份复制进新版本目录。
- 用户只请求更新补丁时，不自动开展新版本逆向适配。明确报告是否需要适配；用户已授权适配时，再检查新入口并修改源码、运行项目测试。
- 恢复成功但源码更新或重新应用失败时，如实说明卡片当前已移除，保留备份和源码。不禁用 Codex 更新，也不通过重装整个 Codex 来回滚。
- 应用补丁无需 `npm install`。只有修改代码并需要界面验证时，才安装开发依赖并运行相应检查；常规维护以工具校验为准。

最终简要报告目标 Codex 版本、源码提交、采取的操作、校验结果和是否需要重新加载窗口。未实际执行的步骤不要声称完成。
